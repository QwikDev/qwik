# Error handling

A route can fail in two ways: the page itself has no answer, such as a missing product, or one piece of its data fails while the rest of the page works. Qwik Router keeps them apart.

## `HttpError`: the page's answer

Throw an `HttpError` from [middleware](/docs/middleware/) or from a blocking [`routeLoader$`](/docs/route-loader/), the default, when the page has no answer. The router renders the nearest `error.tsx` at that status: on the first page load, on client navigation, and when a loader refreshes.

```tsx title="src/routes/product/[id]/index.tsx"
import { component$ } from '@qwik.dev/core';
import { routeLoader$ } from '@qwik.dev/router';
import { HttpError } from '@qwik.dev/router/middleware/request-handler';

export const useProduct = routeLoader$(async ({ params }) => {
  const product = await db.products.findById(params.id);
  if (!product) {
    throw new HttpError(404, 'Product not found');
  }
  return product;
});

export default component$(() => {
  const product = useProduct();
  return <h1>{product.value.name}</h1>;
});
```

A missing product answers with a 404, and the nearest `error.tsx` reads the status and message with `useHttpStatus()`. `throw ev.httpError(404, 'Product not found')` does the same without the import. If the product disappears later, a refresh such as `product.invalidate()` renders the error page too, keeping the URL.

<Note>Thrown anywhere else, such as a `blockSSR: false` loader, a computed or an event handler, an `HttpError` is an ordinary error, handled like the ones below.</Note>

## Other errors

Any other error is a failure of the code that threw it:

- In a loader or a computed with no value yet, reading `.value` throws it to the nearest [`<Catch>`](/docs/labs/catch/). After a refresh, it goes into `.error` and the last value stays beside it.
- In middleware, the router renders `error.tsx` at 500.
- Anywhere else, the nearest `<Catch>` shows its fallback.

Outside development, the message of an error thrown on the server reads "Internal Server Error": the router logs the original and the browser never sees it.

A crash in a blocking loader also fails every loader after it, so the page's data never shows past a failed check. Keep access checks in middleware, where any error renders the error page.

## `server$` errors

A `server$` function answers with the status of the `HttpError` it throws, and the caller receives its data:

```tsx
const getPrices = server$(() => {
  if (!isAuthenticated()) {
    throw new HttpError(401, { code: 401 });
  }

  return fetch('api/product/1/prices');
});

export default component$(() => {
  useVisibleTask$(() => {
    getPrices().catch((err) => {
      // The data of the HttpError is the error caught in the client
      if (err.code === 401) {
        // Navigate to login page
      }
    });
  });

  return <div>Product page</div>;
});
```

## Error interceptor

Intercepting errors with middleware has a few usecases: you might want to add structured error logging, or map the error status codes from RPC API calls to HTTP status codes. This is all achieveable with middleware in a `plugin` file.

<Note>A crash in a loader never passes through `next()`: the router logs it and settles it into the loader's signal.</Note>

```tsx
// src/routes/plugin@errors.ts
import { type RequestHandler } from '@qwik.dev/router'
import { RedirectMessage, HttpError } from '@qwik.dev/router/middleware/request-handler'
import { isDev } from '@qwik.dev/core/build'

export const onRequest: RequestHandler = async ({ next }) => {
  try {
    return await next();
  } catch (err) {
    // Pass through 3xx redirects
    if (err instanceof RedirectMessage) {
      throw err
    }

    // Pass through HttpErrors
    if (err instanceof HttpError) {
      throw err
    }

    // Log unknown errors
    console.error('unknown error', err)

    if (isDev) {
      throw err
    } else {
      throw new HttpError(500, 'Internal server error');
    }
  }
};



```
